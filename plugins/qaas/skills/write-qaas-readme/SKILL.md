# Write a QaaS project README

`qaas-workflow` exclusively owns lifecycle phase selection, authoritative
state, readiness, reviews, and approvals. This domain skill accepts only its
bounded current envelope and returns results to that coordinator.

Documentation is a planned project change, not an onboarding side effect.

- Require approved project context and an approved plan naming the exact README path and intent.
- Preserve the repository's language, layout, tone, and existing user-owned content.
- Describe only evidenced project facts: purpose, boundaries, prerequisites, environment-variable names, exact working directories and commands, what each command covers, configuration composition, suites/cases, samples, hooks/modules, outputs, and troubleshooting that the user requested.
- Cite or link the configured current QaaS documentation for QaaS-dependent claims. Do not copy a changing fact base, hard-code a latest version, or claim runtime validation from build/template evidence.
- Never include credential values, private endpoints not approved for documentation, raw logs, hidden reasoning, or unsupported capabilities.
- Make the smallest useful change. Do not add badges, frameworks, generated diagrams, cleanup, deletion, move, or rename unless explicitly planned—and deletion/move/rename remain user-performed.

Return changed sections, evidence source per material claim, and any unresolved documentation gap.
